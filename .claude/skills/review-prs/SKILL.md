# Review PRs (ESGLite redesign + PCF)

Runs the project's standard PR review on every open pull request into `redesign/integration`, or on the PRs passed as arguments.

## Usage
- `/review-prs` reviews all open PRs targeting `redesign/integration` in CetizionVerifica/ESG-lite_FE, CetizionVerifica/ESG-lite and CetizionVerifica/python_AI_service.
- `/review-prs <PR URL or repo#number> [...]` reviews only those PRs.
- Add `--comment` to also post each PR's review on GitHub (default is read-only: report here only).
- Add `--base <branch>` to review PRs into a different base branch.

## Steps

1. **Collect PRs.** Use the GitHub MCP tools (or `gh` if available). For each repo, list open PRs whose base is `redesign/integration` (or `--base`). Skip drafts only if the user says so; otherwise include them and mark them as draft. If no PRs are found, say so and stop.

2. **Find each PR's spec.** In this order:
   - a spec path named in the PR title or body (e.g. `docs/redesign/pages/P07-...`, `docs/pcf/pages/C02-...`, `docs/pcf/foundation/E1-...`);
   - a `CLAUDE.md` under any `src/features/<module>/` folder the PR touches;
   - the module ID in the branch or title (`[P07 2/4]`, P01–P27, F1–F3, B1–B8, C01–C06, E1–E2) mapped to `docs/redesign/...` or `docs/pcf/...` on the PR's base branch.
   If none is found, review against the definition of done only and say the spec could not be matched.

3. **Review each PR in its own subagent, in parallel** (one Agent per PR, read-only; tell each agent not to push, comment or approve). Give each agent the PR link, the spec path, and this review prompt verbatim:

   > Review PR <link> against its spec <spec path> and the definition of done in docs/redesign/01-plan.md.
   > Check: every behaviour of the old screen is kept or deliberately dropped per the spec; no hex/isDark/slate-* in new code; imports only from src/ui, src/theme and its own feature folder; loading/empty/error states; keyboard + Esc; 390px layout; tests cover moved logic; old route redirects and old files are deleted. For calculation or report code, run the old and new paths on the same data and compare numbers.
   > Report findings ranked by severity with file:line, and say clearly whether it's safe to merge.

   Extra checks by repo:
   - ESG-lite (backend): migrations are additive and reversible, role checks present (User role gets 403 on `/pcf/*`), no change to existing responses unless the spec lists it, tests for the new endpoints.
   - python_AI_service: every AI suggestion returns confidence and reason, unconvertible units are warnings not guesses, nothing is saved without confirmation.
   - PCF engine (E1): golden test within ±0.5%, PcfResult regenerates from factor_snapshot, no result reused as a CBAM figure.
   Also report the PR's CI status and whether it is ≤ ~600 changed lines.

   Each agent returns: verdict (Safe to merge / Merge after fixes / Not safe), findings as `severity · file:line · problem · suggested fix`, CI state, size.

4. **Summarise.** Output one table first: repo, PR (linked), module, verdict, blocking findings count, CI. Then one section per PR with its findings, most severe first. End with the list of PRs that are safe to merge now. Flag any two open PRs that claim the same module ID.

5. **Only with `--comment`:** post each PR's section as a single PR review comment (event COMMENT, never APPROVE or REQUEST_CHANGES), ending with the footer `---` / `_Generated by [Claude Code](https://claude.ai/code)_`. Never merge, approve, push or resolve threads.

## Rules
- Read-only by default. Do not check out and modify PR branches.
- Running tests or old-vs-new number comparisons is allowed in a scratch checkout; never push from it.
- If a PR is too large to review fully, say which files were not reviewed rather than implying full coverage.
